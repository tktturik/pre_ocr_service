# alfa_test

HTTP-сервис предварительной оценки пригодности изображения (PNG, JPEG) или PDF для OCR.

## Архитектура решения

```
HTTP (FastAPI, один процесс uvicorn)
  -> сервис анализа
    -> исполнитель (пул процессов pebble, лимит входа)
      -> воркеры: загрузчик -> проверки -> скоринг (core)
```

Пул процессов pebble (`spawn`): N воркеров создаются и прогреваются при старте. Один документ - одна задача, страницы PDF обрабатываются по одной.

Лимит входа: в работе N задач, в ожидании M (по умолчанию M = N), сверх этого запрос сразу получает 503. Таймаут задачи (60 с) убивает воркер, запрос получает 504. Смерть воркера даёт 500 только его запросу, пул заменяет процесс. Воркер перезапускается после 200 задач: процесс, который долго обрабатывает большие изображения, может понемногу накапливать занятую память, а свежий процесс начинает с чистого состояния. Это ограничивает расход памяти при длительной работе; число задач настраивается (`max_tasks_per_worker`).

Путь в воркере:

1. Формат определяется по сигнатуре файла.
2. Загрузчик строит растры: PNG и JPEG декодируются; страница PDF рендерится в серое с плотностью главного изображения страницы, без растра - 300 DPI.
3. Проверки выполняются последовательно.
4. Скоринг считает вердикт.

Из воркера возвращаются только простые неизменяемые результаты, пиксели не покидают процесс.

Ограничение CPU и памяти: N однопоточных воркеров (OpenMP/BLAS и OpenCV в один поток, пониженный приоритет), лимит входа, таймаут. Пределы:

| Что | Предел |
| --- | --- |
| Тело запроса | 50 МиБ |
| Растр | 40 млн пикселей (изображение больше — 400 до декодирования; страница PDF рендерится с меньшей плотностью) |
| Страниц в PDF | 100 |


### Расширяемость

Проверка - отдельный файл `src/core/checks/<имя>_check.py` с классом-наследником `Check` (`src/core/checks/base_check.py`: `name`, `points`, `measure(ctx) -> float | None`) и константой `CHECK`. Регистрация — строка модуля в `check_modules` (`src/config/settings/analysis.py`); остальной код не меняется.

`src/core/checks/raster_context.py` — общий кэш свойств изображения. Свойства ленивые: считаются один раз и только если их запросила проверка. Доступны серое, карта фона, нормализованное по фону серое, маска чернил по буквенным компонентам, компоненты, высота текста, уровни чернил и фона.

Пример модуля проверки:

```python
from typing import ClassVar

import numpy as np

from core.checks.base_check import Check
from core.checks.raster_context import RasterContext
from core.models.analysis_types import ScorePoints


class InkShareCheck(Check):
    """Доля чернил на странице."""

    name: ClassVar[str] = "ink_share"
    points: ClassVar[ScorePoints] = ScorePoints(bad=0.001, passed=0.01, good=0.05)

    def measure(self, ctx: RasterContext) -> float | None:
        """Возвращает долю чернил или None, если чернил нет."""
        if ctx.ink_mask is None:
            return None
        return float(np.count_nonzero(ctx.ink_mask) / ctx.ink_mask.size)


CHECK = InkShareCheck()
```

Затем в `src/config/settings/analysis.py` в `check_modules` добавляется строка `"core.checks.ink_share_check"`.

Новый формат файла - модуль загрузчика в `src/core/loaders/` и строка в `LOADER_MODULES` (`src/executor/worker_tasks.py`).

## Реализованные проверки

Четыре основные проверки: `resolution`, `blur`, `contrast`, `illumination`. Дополнительные `noise` и `skew` подключены той же регистрацией. В вердикте все запрошенные проверки равноправны.

| Имя | Что выявляет | Как меряет | Порог `passed` |
| --- | --- | --- | --- |
| `resolution` | Мелкий текст, низкое разрешение | Типичная высота букв на странице в пикселях | не менее 5.5 px |
| `blur` | Размытие | Насколько плавно тёмная буква переходит в светлый фон: чем мягче край, тем больше значение, в пикселях | не более 1.9 px |
| `contrast` | Выцветание, слабый контраст | Насколько тёмным выглядит текст на фоне страницы: 0 - текст сливается с фоном, 1 - чёрный на белом; тень на фоне не влияет | не менее 0.13 |
| `illumination` | Тень, неравномерная засветка | Насколько самое тёмное место фона под текстом темнее самого светлого: 0 - освещено ровно, ближе к 1 - сильный перепад | не более 0.48 |
| `noise` | Шум, зернистость | Насколько заметна зернистость по сравнению с контрастом текста; зерно оценивается на самых спокойных участках страницы (поля, промежутки между строк) | не более 0.076 |
| `skew` | Наклон страницы | Типичный угол отклонения строк текста от горизонтали, в градусах; длинные строки влияют сильнее коротких | не более 3.02° |

### Выбор проверок

Выбраны искажения, которые чаще всего ломают распознавание и которые можно измерить без ML: мелкий текст или низкое разрешение (`resolution`), размытие (`blur`), слабый контраст (`contrast`), тень и неравномерная засветка (`illumination`), шум (`noise`), наклон строк (`skew`). Каждая проверка отвечает за свой вид порчи, поэтому по результату видно причину отказа.

### Подбор порогов

Эталон  локальный прогон Tesseract на подобранных страницах и их искусственно ухудшенных копиях с известной силой порчи: размытие, уменьшение, выцветание, шум, тень, JPEG, поворот. К нему добавлена визуальная оценка читаемости. Страница считается нечитаемой, если Tesseract теряет уверенность или заметную долю слов. Порог ставится между читаемыми и нечитаемыми уровнями с запасом, без обучения. Результат проверен на реальных файлах датасета.

## Итоговая оценка качества

У каждой проверки три опорные точки шкалы: `bad` - скор 0, `passed` - 0.5, `good` - 1. Между точками скор считается линейно, за пределами обрезается. Проверка пройдена при скоре не ниже 0.5. Если проверку не удалось измерить (например, нет текста), она провалена со скором 0.

Элемент (изображение или страница PDF):

- пригоден, если прошли все запрошенные проверки;
- `quality_score` - среднее скоров проверок, при провале не выше 0.49.

Документ (PDF) пригоден, если пригодны все его страницы. `quality_score` документа — среднее скоров страниц, при непригодности не выше 0.49. Страница, которая не отрендерилась, непригодна и имеет скор 0.

`processing_time_ms` - время расчёта в воркере, без очереди и сети.

## Результаты benchmark

Замеры проводились отдельным скриптом, где клиент на HTTPX отправляет HTTP-запросы
к сервису, запущенному в Docker-контейнере, и в каждом запросе просит все шесть
проверок. Задержка - время на стороне клиента от отправки запроса до ответа; время
обработки берётся из ответа сервиса. Раз в секунду снимаются загрузка CPU и память
контейнера.

**Замер A: один клиент.** Клиент отправляет запросы по одному, следующий - после ответа на предыдущий. Файлы: 50 изображений и 20 PDF, каждый файл 3 раза (150 и 60 запросов). Перед замером для каждой группы идёт прогрев из пяти запросов, он в результат не входит. Меряем время ответа и время обработки в воркере для изображений и для PDF.

**Замер B: одновременные клиенты.** Одновременно работают C клиентов, каждый шлёт следующий запрос сразу после ответа. Только изображения, 1000 запросов на каждый уровень C, перед уровнем прогрев по C запросов. Уровни C: 1, 2, N/2, N, N+M, 2(N+M), где N - число воркеров, M - длина очереди ожидания. Прогон повторяется для N = 10, 5 и 2 (M = N), контейнер перед каждым N пересоздаётся. Меряем пропускную способность (успешных запросов в секунду), задержку, долю ответов 503, CPU и память контейнера.

| Изображение | 79 | 57 | 250 |

### Замер B

### Выводы

Один запрос обрабатывается для изображения обрабатывается за 79 мс в среднем, p95 250 мс на крупных файлах; для PDF - 409 мс на документ, около 63 мс на страницу. Пропускная способность растёт с числом воркеров: 25 rps при N = 2, 48 при N = 5, 57 при N = 10; при N = 10 рост от N = 5 заметно меньше линейного.

Нагрузка на CPU ограничена числом воркеров: один клиент занимает около одного ядра, а при заполненных воркерах контейнер использует примерно N ядер (902 % при N = 10, 513 % при N = 5, 210 % при N = 2). Память зависит от N и укладывается в ВМ Docker (7,7 ГиБ): пик 1821 МиБ при N = 10, 1015 при N = 5, 646 при N = 2. При перегрузке память не растёт.

Лимит входа работает как задумано: до C = N+M включительно все запросы обслуживаются, ответы 503 появляются только при C > N+M (в замере на уровне 2(N+M)). Ошибок и таймаутов нет, кроме отказов 503 при перегрузке.

## Известные ограничения

1. Перегрузка: когда заняты N мест в работе и M в ожидании, новый запрос сразу получает 503 (`Retry-After: 1`). Очереди сверх M нет.
2. PDF: документ целиком — одна задача. Тяжёлый PDF держит слот, при таймауте теряются все страницы. Не больше 100 страниц.
3. Пустая страница (нет текста) непригодна и делает документ непригодным.
4. Пороги подобраны на ограниченном наборе страниц и по эталону Tesseract. На документах другого типа (рукопись, другие языки, необычная вёрстка) возможны ошибки.
